# zdd-family 仕様・設計

作成日: 2026-09-12

状態: 初版の仕様・設計。実装未着手。

本書群は、集合族を中心にしたライブラリ方針と、プロジェクト名`zdd-family`の合意を文書化したものです。実装開始・crate公開・リポジトリ移動を指示するものではありません。既存の作業ディレクトリ名`zdd-rust`は維持しています。

## 読む順序

1. [仕様](specification.md): 何を保証するか。
2. [公開API契約](api.md): 利用者からどう見えるか。
3. [アーキテクチャ](architecture.md): どこが何を所有・実行するか。
4. [Frontier設計](frontier.md): 問題定義と構築器の契約。
5. [設計判断](decisions.md): 選択の理由と代替案。
6. [Backend適合性評価](backend-evaluation.md): OxiDDと専用coreの比較・採用結果。
7. [検証計画](verification.md): 正しいこと・性能をどう確認するか。
8. [ロードマップ](roadmap.md): 着手順序と未決事項。
9. [関連OSS](related-work.md): 比較の根拠。

## 文書の位置付け

- **要件**: [仕様](specification.md)の`ZF-`識別子を持つ項目。v1または記載した提供段階の受入条件。
- **採用設計**: 実装の初期方針。[設計判断](decisions.md)の変更手続きを経て更新できる。
- **公開API契約**: 所有権、context、ID、失敗、資源制限の互換性境界。細かな名前や引数配置は実装時に調整できるが、契約変更は仕様・ADR・検証を同時に更新する。
- **条件付き設計**: 独自coreを採用する場合など、適用条件を明示した内部方式。
- **未決事項**: [ロードマップ](roadmap.md#4-実装前に決める事項)に判断基準と決定期限を置く。
- **将来案**: v1の完了条件ではない。互換性を阻害しない境界を確保する。

文書間に矛盾が見つかった場合、要件は仕様を基準とし、該当するAPI・設計・検証計画を同時に修正します。文書だけを変更して既存要件を暗黙に取り消してはいけません。

`v1`は最初の安定版1.0、`v1.x`は1.0以降の互換的な追加を指します。0.xの試作版でv1の全要件を提供する必要はありません。

コードブロックは設計を説明する短い例です。`ignore`付きRust例を含め、現在コンパイル・テスト済みのコードはありません。

## 変更管理

仕様変更では、対象要件、理由、互換性、関連API、検証への影響を記録します。設計判断を変更する場合は以前の判断を消さず、置き換えた理由を追記します。実装フェーズへ進んでも、未決事項を既決として扱わないでください。
